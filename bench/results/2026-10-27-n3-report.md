# Paired study with a local model (PLAN.md N3)

This is the model-specific report PLAN.md N3 asks for. Unlike `eval/README.md`,
which documents the harness, every number below comes from a run that actually
happened on this machine, with a real model, on 2026-10-27.

**It is an exploratory result, not an empirical one**, and the record says so
itself: the plan requires 30 independent attempts per task and language, this run
made 2.

## Why the numbers look like this

These are observations from the record and the saved samples, not guesses:

* **The model does not write Nava.** All 30 Nava answers failed to compile. The
  saved samples show two failure modes: Python (`def gcd(a: int, b: int) -> int:`,
  `import math`) and the whole program wrapped in literal `\n` escape sequences
  instead of newlines, which the extractor cannot repair and does not try to.
* **It writes C and C++ that compiles about half the time, and always does the
  wrong thing.** The C/C++ samples read input with prompts on stdout
  (`printf("Enter the first non-negative integer: ")`), call `gcd` without ever
  defining it, and print human sentences instead of one number. 16 of 30 C
  answers and 21 of 30 C++ answers compiled anyway; none of them printed the
  expected output on any case.
* **The repair round never helped.** All 90 attempts used both rounds
  (`median_rounds_used: 2.0`), and the second round — which receives the failing
  test cases as structured feedback — changed nothing: `repair_rate: 0.00`.
* **The completion cap is binding.** 70 of 180 calls (39%) ended with
  `finish_reason: "length"` at 320 tokens; the model rambles (repeat-listed
  docstrings, sample dialogues) instead of emitting one program. 107 of 180
  answers had a tagged code fence, 73 had none or a foreign tag.
* **Nava is charged for its guide, and it shows in prefill.** Median prompt was
  3,660 tokens for Nava against 622 for C: the guide is 4,708 bytes against 447
  for the C prompt, and the prompt is the same text the model was asked to
  answer. That difference is measured, not estimated
  (`eval/measurements/overhead-cl100k_base.json`), and it is why Nava's median
  wall time is 2 s higher even though it generated *fewer* tokens.

## What this result does and does not establish

**It establishes** that the N3 harness runs end to end against a real model with
no API key and no network: prompts, settings, per-round token counts from the
server's own tokenizer, compile and test outcomes inside the isolation boundary,
repairs, aggregates with bootstrap intervals, and a record that a separate
validator re-derives and accepts. It also establishes a floor: a 135M-parameter
instruction model cannot write Nava 0.1 from the guide, cannot fix C or C++ from
compiler and test feedback, and does not benefit from the repair loop at all.

**It does not establish** whether Nava gives a model a shorter time to a correct
answer than C or C++. All three languages are at exactly 0.00 pass@1, and a
uniform zero cannot order three languages. The plan's substantive question stays
open, with a measured reason: this model is below the competence floor at which
any of the three languages is winnable.

**It is not empirical.** Two attempts per task and language, versus the 30 the
plan requires. Reaching the threshold on this machine would take
≈ 990 attempts × 2 calls × ~19 s ≈ **10.4 hours** of the same hardware; on a
GPU-hosted model of, say, 7–14B parameters, where the C/C++ arms would start
passing tests, the cost is dominated by the vendor, not by this repository.

**It does not generalize.** One 135M model, one temperature, one completion
cap, one repair round. Nothing here is evidence about larger models, about
temperature, or about Nava's design beyond the observation that a model without
prior exposure to the language writes something else.

## Reproducing it

```bash
python3 -m pip install --index-url https://download.pytorch.org/whl/cpu torch
python3 -m pip install transformers

python3 tools/local_model_server.py \
  --model HuggingFaceTB/SmolLM2-135M-Instruct \
  --revision 12fd25f77366fa6b3b4b768ec3050bf629380bac \
  --host 127.0.0.1 --port 8765 --threads 2 --max-tokens 1024 &

NAVA_LOCAL_KEY=local python3 eval/study.py --provider openai \
  --model HuggingFaceTB/SmolLM2-135M-Instruct \
  --base-url http://127.0.0.1:8765/v1 --api-key-env NAVA_LOCAL_KEY \
  --held-out /path/outside/the/repo/nava-N3-heldout.json \
  --languages nava,c,cpp --attempts 2 --repair-rounds 1 \
  --temperature 0.2 --max-tokens 320 --isolation auto \
  --out bench/results/<date>-n3-study-smollm2-135m.json

python3 eval/check_study_record.py \
  bench/results/<date>-n3-study-smollm2-135m.json --require measured
```

The held-out task file is not in this repository by design; the record pins it by
SHA-256 (`plan.task_files`), and the tasks themselves are four numeric tasks with
27 cases (`lcm_two`, `modexp`, `count_odd_digits`, `triangle_kind`), each checked
against an independent oracle before the run. The weights were loaded at
revision `12fd25f7…`, so re-running later gets the same model, and the server
seeds each call from `--seed`, so the samples reproduce with the same thread
count.
